# Portico — Feature specification (clean-room)

Feature parity checklist for the clone. Deliberately no reference to the original app — implement from this list alone. The clone may (and should) rename everything.

## Components

- **Server daemon** — shares locally-attached devices over the network; runs headless (foreground service on Android).
- **Server GUI app** — status screen + settings menus; talks to the daemon over a local control channel (documented, line-based text protocol; name your own channel).
- **Boot receiver** — starts the daemon after reboot when the "start on boot" toggle is on.
- **Permission flow** — runtime prompt per attached device on first use; remembered grants.

## Ignored devices

- Persistent list of `vid/pid` hex pairs (e.g. `0123/AE3C`), validated input + "select from attached list" picker (entries formatted `product name(vvpp)`), checkbox remove flow with validation toasts.
- Attached devices in the list are never auto-shared when ignored; everything else is.

## Reverse clients

- Persistent list; the server accepts/creates connections for them; CRUD like ignored list.

## Daemon feature surface (control-channel commands to implement)

register client / unregister client; get/set daemon state; start/stop server process; ignored-list set/get; reverse-clients set/get; relay enable/disable + address + status; shutdown; network-lock set/unset; wake-lock set/unset; speed setting; device list + device events.

## Networking

- Server listens on its own TCP port (versioned protocol; define your own port number).
- UDP/relay discovery for NAT traversal (the "put the address above into any client" path).
- Desktop clients can list, claim, and use attached devices concurrently; two devices at the same time must work (app is free — no seat/count gating).

## Security

- **TLS by default.** Connections to anything beyond the LAN must be TLS; plaintext is an explicit per-toggle opt-in intended for the LAN only, shown with a warning label in the GUI. (A USBIP session is a raw pipe to the device — serial consoles, filesystems, keystrokes — so carrier/internet paths without TLS are never acceptable.)
- **Pairing = TOFU + fingerprint pin.** On first contact the client displays a short fingerprint of the server certificate; the user confirms once and it is pinned thereafter. No CA, no online checks — pairing works fully offline.
- **Reverse clients require mutual TLS** — outbound-initiated connections must never trust the dialed party by address alone; both sides authenticate before session start. The reverse-client list acts as an explicit allowlist.
- **Relay sees ciphertext only.** The relay/NAT path learns nothing beyond bytes and port metadata; the key exchange is end-to-end between server and client.
- **Basic authentication = claim token.** A claim/access token auto-generated by the daemon at first run (viewable and regenerable in the GUI) must be presented by any client before it can list or claim devices. User accounts (multi-user usernames/passwords) are out of scope for v1; the token is replaced by per-credential accounts later without protocol redesign (handshake carries a credentials field already).
- **Auth is protocol-level, not HTTP-level.** The token rides inside the versioned handshake under TLS — HTTP Basic headers are not used.
